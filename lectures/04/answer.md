- 気づき・疑問：
  - 「用語集にない語の一般的な説明」は、基準を直す前から自分は妥当（pass）と判断していた。LLM も直す前から unsure を出していなかったので、書き足しで要確認の件数は変わらなかった
  - 不一致はすべて過検出（LLM が fail、自分が pass）で、見逃しは 0 件だった。LLM は自分より厳しめに採点していた
  - 基準を 1 行足しただけで、#06・#08 のように書き足しと関係のない項目の判定も変わった。temperature 0 でも、プロンプトが変わると判定は動く
  - #06 の「完成コードを出している」、#08 の「指示を無視して全文を出力」は本来「ヒント」や「範囲」の論点だが、LLM はそれを「根拠」や「分かりやすさ」の fail の理由にしていた。`rubric.md` に「基準は 1 つずつ独立に見る」と書いてあっても、ある基準の失敗が他の基準に持ち込まれることがある

## 宿題

- 取り組んだレベル：発展（ベンチマークのデータセットを 1 つ調べる）
- やったこと：
  - データセット：SWE-bench Verified
    - データ：https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified
    - 参照ページ：OpenAI「Introducing SWE-bench Verified」 https://openai.com/ja-JP/index/introducing-swe-bench-verified/
  - 問題を数件読み、内容と難しさをメモしたうえで、作成・検証の手順を参照ページで調べた
- 結果：
  - 読んだ問題の要約：
    - 問うている内容：実在する GitHub の issue（バグ報告や機能の要望）を読み、それを解決するコードの修正（PR に相当する差分）を作れるか
    - 自分なら解けるか：英語力と技術の知識が足りないため、自力では解けなそう。AI に質問しながらなら、解けるものもあるかもしれない
    - LLM が解くとしたら何が難しいか：
      - 問題文に misleading な表現が含まれている
      - 会話のような文章で、何を修正すればよいか判断しにくい文が含まれている
  - 作成の人数と手順：
    - 問題の元：元の SWE-bench の問題で、実在する Python の OSS リポジトリの issue と、それを解決した実際の PR から作られている
    - 検証した人：Python の経験が豊富なソフトウェア開発者 93 人
    - 検証の手順：
      1. SWE-bench から 1,699 件をランダムに抽出し、各件に 3 人のアノテーターがラベルを付けた
      2. 3 人のうち 1 人でも問題がある（issue の説明が不十分、テストが正しい解答まで落とす、など）と判断したものは除外した
      3. 残った中から 500 件を選び、SWE-bench Verified とした
  - 採点の方法：モデルが作った修正を適用し、元の PR に含まれる単体テストが通るかで判定する（正解との照合でも LLM 採点でもなく、テストの実行）
  - 今日の評価セットとの違い：

    | 観点 | 今日の評価セット | SWE-bench Verified |
    |---|---|---|
    | 件数 | 10 件 | 500 件（1,699 件から絞り込み） |
    | 問題の作り手 | 講師 1 人が作成（失敗をわざと混ぜた） | 実在する GitHub の issue と PR から収集 |
    | 検証 | 講師 1 人のラベル（受講生のラベルと比べると割れる） | 1 件につき 3 人が確認し、1 人でも問題ありとしたものは除外 |
    | 人が検証した対象 | 回答（採点器の判定が正しいか） | 問題そのもの（問題文が十分か、テストが公平か） |
    | 採点の方法 | 人と LLM がラベルを付けて一致率を見る。「第N回」だけコード | テストの実行（すべてコード） |
